# 资源账本数据字典、冷热分层与快照协议 (ledger-model)

> 规范版本：v1.0  
> 适用专员：Agent A（资源审计专员 / Asset Auditor）  
> 协同引擎：`scripts/ledger_engine.py`、主审查协调器

---

## 一、系统定位与设计哲学

在百万字长篇网络小说连载中，“资产失忆”是造成作品崩盘的核心顽疾之一：
1. 前文历尽千辛万苦夺来的至宝，三卷之后作者彻底遗忘；
2. 已经消耗殆尽的救命九转还魂丹，后文危急时刻无端再度现身；
3. 主角借给师妹防身的灵剑，转头主角自己又拔剑斩敌；
4. 战斗中突然掏出未曾交代的全新外挂，引发读者狂喷“机械降神”。

本系统采用**双轨存储架构**与**确定性状态机**，构建军工级资产追踪防护网，既满足作者日常写作的可视化翻查，又锁死机器端精确的事实唯一源（SSOT）。

## 二、双轨存储与人机协同机制

### 2.1 双轨存储架构

| 存储端 | 物理路径 | 核心受众 | 读写权限 | 功能职责 |
| :--- | :--- | :--- | :--- | :--- |
| **人类端** | `设定/资源账本.md` | 作家本人 | 人类只读/人工编辑 | 提供分类表格与卡片视图，方便码字时直观查阅当前持有的底牌、丹药结余与战力状态。 |
| **机器端** | `设定/资源账本.json`（兼容根目录 `资源账本.json`） | 审查引擎 / Agent A | 机器写入 / SSOT | 系统的**单一事实源（Single Source of Truth）**。保存资产、归属人与历史流水；Markdown 作为可编辑视图，修改后需显式同步。 |

### 2.2 防丢失脏写拦截契约 (Dirty-Write Guard)

为防止自动化审查脚本覆写作者在 Markdown 账本中手动增删的珍贵构思，底层严格执行时间戳防脏写拦截：
1. **时间戳比对 (mtime check)**：
   - 每次引擎准备根据 JSON 重新渲染 `设定/资源账本.md` 前，必须对比两者的物理修改时间。
   - 若 `mtime(Markdown) - mtime(JSON) > 0.05 秒`，视为可能存在未同步的手工修改；容差用于适配文件系统时间戳精度。
2. **拦截与告警**：
   - 脚本立即终止自动覆写，打印防御告警：
     ```
     [Ledger Dirty Warning] 检测到 Markdown 账本存在未同步的人工修改，已暂停自动覆写。
     请先调用: sync_ledger_from_md(project_dir)
     确认需要强制覆盖时，向相应 API 传入 force=True。
     ```
3. **反向同步流水线 (`sync_ledger_from_md(project_dir)`)**：
   - 解析 Markdown 账本表格，反向提取增量资产与数量变动，校验通过后合入 JSON，刷新时间戳。

### 2.3 双轨保存失败恢复

保存前先生成两轨内容，并为已有文件保留原字节与时间戳副本。第二轨写入失败时恢复原文件；若外部文件锁等原因阻止恢复，保留同目录的 `.资源账本.json.recovery.json` 标记及 `.recovery-*.bak` 副本，相关 API 返回 3，`force=True` 也不能绕过。

恢复时先解除文件占用，依据标记的 `phase`、`targets` 和 `backup` 核对两轨及仍存在的副本，确认原文件均已恢复后再移除标记。已成功恢复的副本可能已被原子替换消耗；不要仅删除标记来重新启用不一致账本。该机制提供失败恢复信息，不等同于文件系统对两个文件提供原子事务。

## 三、资产分类与数据字典

当前 Python 模型使用下列中文 `category` 值，`身份权限` 兼容旧分类名称。表中的核对要求供专家结合正文验证，分类本身不代表相关事实已获确认。

| 资产类型 (Category) | 包含范例 | 核心审计重点 | 数量/状态约束 |
| :--- | :--- | :--- | :--- |
| **资金资产** | 灵石、铜钱、宗门贡献点、神魔积分、黄金 | 收入与支出是否吻合 | 数值数量及支出来源 |
| **装备道具** | 本命飞剑、护心镜、乾坤储物袋、传送阵钥匙 | 随身携带、完好度、借出归属 | 唯一 ID、实际持有人和状态 |
| **丹药耗材** | 回气丹、破境丹、蚀骨散、雷火符、爆裂弹药 | 是否已耗尽、是否有补充来源 | 数量、消耗历史及 CONSUMED 状态 |
| **功法神通** | 焚天诀、浮光掠影步、重瞳被动、九重暗劲 | 境界前置、冷却、反噬代价 | 在 constraints 中记录约束，按正文核对 |
| **身份特权**（兼容 **身份权限**） | 宗门真传令、城主虎符、秘境通关铭牌 | 有效期、权限范围、挂失 | 授予与失效事实 |
| **随行战力** | 契约灵兽、替身傀儡、护道暗卫 | 伤势、召唤条件、战死闭环 | 持有人、状态及约束 |
| **地契房产** | 房产、田亩、封地 | 归属与转让 | 数量、面积单位及所有者 |
| **规则诡器** | 规则道具、诡异物品 | 触发条件与使用代价 | 约束和状态 |
| **全局状态** | 绝灵压制、剧毒、血脉封印、易容 | 持续时间及解除条件 | 以实际资产状态枚举与约束表达 |

### 3.1 当前 Python 账本 JSON 结构

以下示例由 `LedgerState.to_dict()` 生成，可直接通过 `LedgerState.from_dict()` 读取。资产按 ID 存入顶层 `assets`，不使用旧概念示例中的 `entities` 嵌套结构。`constraints` 保存附加约束，是否符合正文事实仍需宿主核验。

```json
{
  "last_updated_chapter": 31.0,
  "assets": {
    "eq_frost_sword": {
      "id": "eq_frost_sword",
      "name": "霜华剑",
      "category": "装备道具",
      "quantity": 1,
      "unit": "柄",
      "owner": "顾渊",
      "current_holder": "顾渊",
      "status": "EQUIPPED",
      "origin_chapter": 12.0,
      "lend_meta": null,
      "constraints": {
        "min_realm": "练气九层"
      },
      "history": []
    }
  },
  "foreshadowing_stash": [
    {
      "name": "九龙玉玺",
      "origin": "第10章秘境暗格",
      "status": "CONCEALED"
    }
  ]
}
```

`foreshadowing_stash` 保存正文显式标签的名称、来源和状态；其状态文本与资产枚举分开，不会自动把伏笔登记成正式资产。

## 四、资产生命周期与专家核验规则

下图是叙事核验的概念流程，不是 Python 强制执行的状态转移表。当前 `AssetItem.transition()` 校验目标状态名称，更新借还/转让信息并记录历史；不会自行判断正文因果、耐久变化或约束是否满足。实际状态包括 `UNACQUIRED`、`ACQUIRED`、`EQUIPPED`、`CONSUMED`、`DAMAGED`、`TRANSFERRED`、`LENT_OUT`、`RECLAIMED`、`RESTORED`。归还和修复可分别记录为 `RECLAIMED`、`RESTORED`，后续装备另行记录。

```
          ┌──────────────────────────────────────────────┐
          │                 UNACQUIRED                   │
          └──────────────────────┬───────────────────────┘
                                 │ ACQUIRE（获取/掉落/缴获）
                                 ▼
          ┌──────────────────────────────────────────────┐
          │                  ACQUIRED                    │
          └───────────┬──────────────────────┬───────────┘
                      │ EQUIP（装备/随身佩戴） │ TRANSFER（转让/出售）
                      ▼                      ▼
┌──────────────────────────────┐     ┌──────────────────────────────┐
│           EQUIPPED           │     │         TRANSFERRED          │
└──┬───────────┬──────────────┬┘     └──────────────────────────────┘
   │           │              │
   │ CONSUME   │ LEND_OUT     │ DAMAGE（损毁/折断）
   ▼           ▼              ▼
┌────────────┐┌─────────────┐┌────────────┐
│ CONSUMED   ││  LENT_OUT   ││  DAMAGED   │
└────────────┘└──────┬──────┘└─────┬──────┘
                     │             │
                     │ RECLAIM     │ REPAIR / RESTORE
                     ▼             ▼
              ┌───────────────────────────┐
              │         ACQUIRED          │
              └───────────────────────────┘
```

### 4.1 需要专家核验的状态迁移约束
1. **消耗锁定**：处于 `CONSUMED`（已消耗）状态的道具（如已服用的丹药），严禁直接转回 `EQUIPPED`。若后文再度出现同名道具，必须具备新的 `ACQUIRE` 动作流水。
2. **损毁判定**：处于 `DAMAGED` 状态的法宝，需依正文设定核对剩余效果、修复条件与使用代价，不自动假定碎裂或反噬。
3. **借还闭环**：处于 `LENT_OUT` 状态的资产，原主人的当前动作判定中不具备该道具使用权；持有人归还后触发 `RECLAIM` 方可复原。

## 五、暗线伏笔缓冲池与多主体暂借协议

### 5.1 暗线伏笔缓冲机制 (Foreshadowing Stash)

在优秀网文中，作者常采用“暗线伏笔”：故意不向读者摊牌主角在某个秘境搜括的底牌，而在数十章后的绝境突然祭出，形成强烈的反转爽点。

为了杜绝审查系统“误杀”作者精心埋设的伏笔，引入**伏笔缓冲池协议**：
1. **正文隐形注释语法**：
   作者可在正文 Markdown 中埋入隐形 HTML 审计注释：
   `<!-- audit:stash name="九龙玉玺" origin="第10章秘境暗格" status="CONCEALED" -->`
   支持 HTML 注释的 Markdown 渲染器会隐藏该标记；纯文本阅读或投稿时仍需按目标平台格式处理。
2. **上下文线索智能探测**：
   当正文中突然祭出一件账本中未收录的核心道具时，Agent A 首先检索正文前文是否存在隐形注释，或是否存在暗扣动作线索（如“抚摸怀中硬物”、“早已悄然握紧底牌”）。
3. **降级处置而非强行阻断**：
   - 命中文中暗线伏笔时，Agent A **严禁**直接定性为“P1 凭空出装”破坏高潮；
   - 降级为 `[P2 待认领伏笔提示]`，并在报告中输出一键补登指令，提示作者是否将该伏笔转为正式亮相状态。

### 5.2 多主体资产所有权流转 (Multi-Entity Ownership)

网文涉及复杂的配角互动与灵宠战斗：
- 主角将武器借给同道护身；
- 战宠自主吞噬灵石消耗储备；
- 宗门长辈赐予限次防护玉符。

**流转协议规范**：
- 资产记录包含 `owner`（归属人）与 `current_holder`（实际持有人）。
- 当陆雪手持主角借出的“霜华剑”阻击妖兽时，Agent A 核验 `current_holder == "陆雪"` 且 `status == "LENT_OUT"`，再结合正文确认借出来源与时序。
- 严禁误判为陆雪“凭空持剑”，同时防止原主人在同一时间线“分身拔剑”。

## 六、凭空出装双方案短句修复机制

当章节中确实出现了既无账本记录、又无伏笔暗线的凭空出装时，Agent A 必须向作者输出两种可直接合入正文的短句修复方案：

### 方案 1【前置补源 / 追溯交代】
* **适用场景**：该道具对当前破局、装逼打脸或主线推进极为关键，不可删换。
* **短句范例**：
  > 顾渊反手自袖中摸出一张金光黯淡的符箓。  
  > 昨夜击杀黑煞教分舵舵主缴获的三阶破煞符。  
  > 一直贴身藏在护心镜后。  
  > 此刻正好派上用场。
* **账本联动**：宿主在事实确认后另行增补第 30 章缴获记录；`apply_fix()` 本身只回写正文，不自动补写账本。

### 方案 2【就地修正 / 等价平替】
* **适用场景**：该道具并非不可替代的核心，使用已有底牌或环境借力同样能精彩破局。
* **短句范例**：
  > 顾渊没有掏符。  
  > 而是反手拔出腰间青钢剑，剑尖斜挑，狠狠擦过岩壁。  
  > 火星迸溅。  
  > 引燃了石缝间积聚百年的地煞阴火。  
  > 烈焰轰然腾空，化作火龙吞噬了扑来的妖蝠。
* **账本联动**：无需在账本中增设新道具，直接消耗现有资源，杜绝资产恶性通胀。

## 七、长篇处理方式与当前性能边界

长篇处理需要分别评估章节扫描、账本大小与宿主的上下文预算。当前实现如下，不承诺所有项目均能秒级完成或保持固定 Token 消耗：

### 1. 首次建账流式增量管道 (Streaming Incremental Init)
- 调用 `init_ledger(project_dir, scope_str="1-100")` 时；
- 严禁一次性将百章全量正文喂入 LLM 上下文（否则瞬间撑爆 Context Window 且严重幻觉）；
- 底层 Python 引擎逐章读取并启发式提取候选资产，在内存中合并账本后保存；该步骤不调用 LLM，也不等于专家已核实全部资产。

### 2. 分卷封账快照协议 (Snapshot Checkpoint)
- 每卷连载完毕（如第 100 章），调用 `checkpoint_volume(project_dir, volume=1)`。
- 当前完整账本快照保存至 `设定/archive/volume_01_ledger.json`。
- 快照操作不会自动裁剪主账本或删除历史流水，也没有 15KB 的主账本大小保证。

### 3. 冷热资产动态分层 (Hot / Cold Tiering)
- **热资产（Hot Tier）**：主角随身装备、核心神通、正在生效的状态、契约灵兽。展示在 Markdown 账本首屏。
- **冷资产（Cold Tier）**：已经耗尽的丹药、折断损毁的旧武器、过期的入门令牌。在 Markdown 视图中分区展示，仍保留在 JSON 数据源中。

### 4. 预审包中的账本规模
- `pre_audit_bundle.json` 当前包含账本资产，并将每项资产的历史流水截取为最近 5 条；尚未按本章实体自动筛选局部资产。
- 预审包大小随资产数量增长。宿主发送给专家前应按实际审查任务选择上下文，并明确被省略的范围。
