# 资源账本数据字典、冷热分层与快照协议 (ledger-model)

> 规范版本：v1.0  
> 适用专员：Agent A（资源审计专员 / Asset Auditor）  
> 协同引擎：`scripts/ledger_engine.py`、主审查协调器

## 一、系统定位与设计哲学

在百万字长篇网络小说连载中，“资产失忆”是造成作品崩盘的核心顽疾之一：
1. 前文历尽千辛万苦夺来的至宝，三卷之后作者彻底遗忘；
2. 已经消耗殆尽的救命九转还魂丹，后文危急时刻无端再度现身；
3. 主角借给师妹防身的灵剑，转头主角自己又拔剑斩敌；
4. 战斗中突然掏出未曾交代的全新外挂，引发读者狂喷“机械降神”。

本系统采用**双轨存储架构**与**确定性状态机**，构建军工级资产追踪防护网，既满足作者日常写作的可视化翻查，又锁死机器端精确的事实唯一源（SSOT）。

## 二、双轨存储与人机协同机制

### 2.1 双轨存储架构

| 存储端 | 物理路径 | 核心受众 | 读写权限 | 功能职责 |
| :--- | :--- | :--- | :--- | :--- |
| **人类端** | `设定/资源账本.md` | 作家本人 | 人类只读/人工编辑 | 提供分类表格与卡片视图，方便码字时直观查阅当前持有的底牌、丹药结余与战力状态。 |
| **机器端** | `追踪/resource_ledger.json` | 审查引擎 / Agent A | 机器排他写入 / SSOT | 系统的**单项事实源（Single Source of Truth）**。存储全生命周期流水、时间戳、归属人与校验和。 |

### 2.2 防丢失脏写拦截契约 (Dirty-Write Guard)

为防止自动化审查脚本覆写作者在 Markdown 账本中手动增删的珍贵构思，底层严格执行时间戳防脏写拦截：
1. **时间戳比对 (mtime check)**：
   - 每次引擎准备根据 JSON 重新渲染 `设定/资源账本.md` 前，必须对比两者的物理修改时间。
   - 若 `mtime(Markdown) > mtime(JSON)`，说明作者手动修改了 Markdown 且尚未同步到机器端。
2. **拦截与告警**：
   - 脚本立即终止自动覆写，打印防御告警：
     ```
     [Ledger Dirty Warning] 检测到 Markdown 账本存在未同步的人工修改，已暂停自动覆写。
     请先执行: python scripts/story_audit.py --sync-from-md
     或追加参数: --force 强制覆盖。
     ```
3. **反向同步流水线 (`--sync-from-md`)**：
   - 解析 Markdown 账本表格，反向提取增量资产与数量变动，校验通过后合入 JSON，刷新时间戳。

## 三、七类资产数据字典与定义

所有资产划分为 7 大类型，每类资产具有专属的校验基线与数据约束：

| 资产类型 (Category) | 包含范例 | 核心审计重点 | 数量/状态约束 |
| :--- | :--- | :--- | :--- |
| **currency (资金资产)** | 灵石、铜钱、宗门贡献点、神魔积分、黄金 | 数量结余平衡，严禁支出大于收入产生赤字 | 仅支持数值计数（非负整数/浮点），严禁透支 |
| **equipment (装备道具)** | 本命飞剑、护心镜、乾坤储物袋、传送阵钥匙 | 随身携带状态、完好度、借出归属、封印与损毁 | 具有唯一性 ID，跟踪持有人与耐久度 |
| **consumable (丹药耗材)** | 回气丹、破境丹、蚀骨散、雷火符、爆裂弹药 | 一次性消耗，严禁已耗尽消耗品无前置补充再度使用 | 严格扣减，归零后状态锁定为 CONSUMED |
| **technique (功法神通)** | 焚天诀、浮光掠影步、重瞳被动、九重暗劲 | 境界前置限制、冷却周期、反噬代价与层数推进 | 记录修炼层级、领悟章位与施展代价 |
| **credential (身份权限)** | 宗门真传令、城主虎符、秘境通关铭牌、客卿玉牒 | 有效期、势力覆盖范围、挂失与被剥夺状态 | 记录授予势力与权限失效事件 |
| **companion (随行战力)** | 契约噬金虫、玄武神兽、替身傀儡、护道暗卫 | 伤势状态、饱食度/灵力、召唤限制、战死闭环 | 具有独立生命周期与状态槽，支持自主损耗 |
| **status (全局状态)** | 绝灵压制、九幽剧毒、血脉封印、易容改貌伪装 | 持续时限、解除条件、全属性削弱百分比 | 具有时间窗口，超期必须触发解除或毒发 |

## 四、资产全生命周期状态机与合法转移规则

```
          ┌──────────────────────────────────────────────┐
          │                 UNACQUIRED                   │
          └──────────────────────┬───────────────────────┘
                                 │ ACQUIRE（获取/掉落/缴获）
                                 ▼
          ┌──────────────────────────────────────────────┐
          │                  ACQUIRED                    │
          └───────────┬──────────────────────┬───────────┘
                      │ EQUIP（装备/随身佩戴） │ TRANSFER（转让/出售）
                      ▼                      ▼
┌──────────────────────────────┐     ┌──────────────────────────────┐
│           EQUIPPED           │     │         TRANSFERRED          │
└──┬───────────┬──────────────┬┘     └──────────────────────────────┘
   │           │              │
   │ CONSUME   │ LEND_OUT     │ DAMAGE（损毁/折断）
   ▼           ▼              ▼
┌────────────┐┌─────────────┐┌────────────┐
│ CONSUMED   ││  LENT_OUT   ││  DAMAGED   │
└────────────┘└──────┬──────┘└─────┬──────┘
                     │             │
                     │ RECLAIM     │ REPAIR / RESTORE
                     ▼             ▼
              ┌───────────────────────────┐
              │         ACQUIRED          │
              └───────────────────────────┘
```

### 4.1 核心状态迁移规则约束
1. **消耗锁定**：处于 `CONSUMED`（已消耗）状态的道具（如已服用的丹药），严禁直接转回 `EQUIPPED`。若后文再度出现同名道具，必须具备新的 `ACQUIRE` 动作流水。
2. **损毁判定**：处于 `DAMAGED` 状态的法宝，未执行修复前不可发挥全额威能，强行催动将导致法宝彻底碎裂并反噬主人。
3. **借还闭环**：处于 `LENT_OUT` 状态的资产，原主人的当前动作判定中不具备该道具使用权；持有人归还后触发 `RECLAIM` 方可复原。

## 五、暗线伏笔缓冲池与多主体暂借协议

### 5.1 暗线伏笔缓冲机制 (Foreshadowing Stash)

在优秀网文中，作者常采用“暗线伏笔”：故意不向读者摊牌主角在某个秘境搜括的底牌，而在数十章后的绝境突然祭出，形成强烈的反转爽点。

为了杜绝审查系统“误杀”作者精心埋设的伏笔，引入**伏笔缓冲池协议**：
1. **正文隐形注释语法**：
   作者可在正文 Markdown 中埋入隐形 HTML 审计注释：
   `<!-- audit:stash name="九龙玉玺" origin="第10章秘境暗格" status="CONCEALED" -->`
   该注释在阅读软件中完全隐形，不影响正文呈现。
2. **上下文线索智能探测**：
   当正文中突然祭出一件账本中未收录的核心道具时，Agent A 首先检索正文前文是否存在隐形注释，或是否存在暗扣动作线索（如“抚摸怀中硬物”、“早已悄然握紧底牌”）。
3. **降级处置而非强行阻断**：
   - 命中文中暗线伏笔时，Agent A **严禁**直接定性为“P1 凭空出装”破坏高潮；
   - 降级为 `[P2 待认领伏笔提示]`，并在报告中输出一键补登指令，提示作者是否将该伏笔转为正式亮相状态。

### 5.2 多主体资产所有权流转 (Multi-Entity Ownership)

网文涉及复杂的配角互动与灵宠战斗：
- 主角将武器借给同道护身；
- 战宠自主吞噬灵石消耗储备；
- 宗门长辈赐予限次防护玉符。

**流转协议规范**：
- 资产记录包含 `owner`（归属人）与 `current_holder`（实际持有人）。
- 当陆雪手持主角借出的“霜华剑”阻击妖兽时，Agent A 核验 `current_holder == "陆雪"` 且 `status == "LENT_OUT"`，判定为**完全合规**。
- 严禁误判为陆雪“凭空持剑”，同时防止原主人在同一时间线“分身拔剑”。

## 六、凭空出装双方案短句修复机制

当章节中确实出现了既无账本记录、又无伏笔暗线的凭空出装时，Agent A 必须向作者输出两种可直接合入正文的短句修复方案：

### 方案 1【前置补源 / 追溯交代】
* **适用场景**：该道具对当前破局、装逼打脸或主线推进极为关键，不可删换。
* **短句范例**：
  > 顾渊反手自袖中摸出一张金光黯淡的符箓。  
  > 昨夜击杀黑煞教分舵舵主缴获的三阶破煞符。  
  > 一直贴身藏在护心镜后。  
  > 此刻正好派上用场。
* **账本联动**：自动在账本历史中增补第 30 章缴获记录，保持事实自洽。

### 方案 2【就地修正 / 等价平替】
* **适用场景**：该道具并非不可替代的核心，使用已有底牌或环境借力同样能精彩破局。
* **短句范例**：
  > 顾渊没有掏符。  
  > 而是反手拔出腰间青钢剑，剑尖斜挑，狠狠擦过岩壁。  
  > 火星迸溅。  
  > 引燃了石缝间积聚百年的地煞阴火。  
  > 烈焰轰然腾空，化作火龙吞噬了扑来的妖蝠。
* **账本联动**：无需在账本中增设新道具，直接消耗现有资源，杜绝资产恶性通胀。

## 七、百万字长篇抗膨胀四大设计

为保障小说连载至千章规模时，审查系统仍能秒级响应且 Token 消耗平稳，必须严格遵守以下四大抗膨胀架构：

### 1. 首次建账流式增量管道 (Streaming Incremental Init)
- 执行 `python scripts/story_audit.py --init --scope 1-100` 时；
- 严禁一次性将百章全量正文喂入 LLM 上下文（否则瞬间撑爆 Context Window 且严重幻觉）；
- 底层 Python 引擎采用流式单章管道：逐章扫描提取增量变更，在内存中完成状态机迭代，仅输出最新账本快照，Token 消耗控制在 $O(N)$ 黄金线。

### 2. 分卷封账快照协议 (Snapshot Checkpoint)
- 每卷连载完毕（如第 100 章），执行：`python scripts/story_audit.py --checkpoint --volume 1`。
- 历史章节所有细碎流水（如哪一章吃了两块碎银子、喝了几瓶低阶金创药）归档封存至 `追踪/archive/volume_01_ledger.json`。
- 仅提炼当期“期末净资产清单”（随身核心法宝、本命功法、境界、大额灵石）作为下一卷的初始基线。主账本上下文永久控制在 15KB 以内。

### 3. 冷热资产动态分层 (Hot / Cold Tiering)
- **热资产（Hot Tier）**：主角随身装备、核心神通、正在生效的状态、契约灵兽。展示在 Markdown 账本首屏。
- **冷资产（Cold Tier）**：已经耗尽的丹药、折断损毁的旧武器、过期的入门令牌。自动折叠或移入归档区，不再参与日常实时审计。

### 4. 按章动态投影 (On-Demand Projection)
- 日常单章审查时，Python 预检器先提取本章出现的角色名、武器名、功法名，仅将与本章实体相关的局部账本切片装配至 `pre_audit_bundle.json`。
- Agent A 审查单章仅需读取极简切片，实现真正的 $O(1)$ 常数级轻量化送审。
